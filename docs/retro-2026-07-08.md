# 2026-07-08 변경 리포트 — 백그라운드 생성, 그리고 유령 사냥 복기

> 목적: 오늘 하루 동안의 수정을 항목별로 "필수였나 / 유익했나 / 과했나"로 판정하고,
> 오진 과정을 기록해 다음에 같은 함정을 피하기 위한 복기 문서.
> 최종 상태: 전부 main에 머지 완료(`87f9b58`, --no-ff), 브랜치는 검증 후 삭제,
> 회귀 테스트 29개가 `tests/`로 승격됨 (§6 참고).

## 1. 발단

윈도우 설치본(setup.bat)이 WSL 대비 눈에 띄게 느리고, ① 질문 생성 도중 다른
페이지로 이동하면 생성이 끊기며 결과가 유실된다는 문제 제기로 시작.

## 3. 오진 복기 — 실제 원인은 코드가 아니었다

- **실제 원인**: 동료 시나리오 테스트용으로 run.bat이 띄워 둔 **구버전 서버가 8501을
  점유**하고 있었고, WSL2는 localhost를 윈도우와 공유하므로 브라우저는 계속 구버전
  코드에 접속하고 있었다. "수정했는데 차이가 없다", "내용은 ①인데 불은 ②" 모두
  수정 전 코드의 증상이었다.
- **놓친 것**: "브라우저가 어느 서버(코드)에 붙어 있는가"라는 전제를 검증하지 않고
  코드 레벨 가설(rerun 경쟁 조건 → 위젯 프런트엔드 desync)로 직행했다.
- **시그널은 있었다**: 서버 측 자동화 테스트(AppTest)는 일관되게 정상인데 브라우저
  관찰만 이상했다. *서버 측 정상 + 브라우저만 이상 = 코드보다 연결 대상부터 의심.*
- **재발 방지**: 사이드바에 데이터 경로가 표시되므로(WSL `/home/...` vs 윈도우
  `C:\...`) 어느 인스턴스인지 3초 만에 판별 가능. 양쪽 동시 구동 시에는
  `--server.port 8502`로 포트 분리.

## 4. 남은 트레이드오프 / 알려진 한계

- **생성 완료 후 인라인 미리보기 표가 사라짐** — 동기 생성 시절에는 완료 직후 생성분
  표가 떴다. 지금은 사이드바 완료 알림 + "질문 정리" 표(대기열 순)로 확인. 아쉬우면
  "이번 생성분만 보기"를 추가로 복원 가능.
- **완료 전환 시 fragment발 전체 rerun 1회** — 폴링 종료용. 키 있는 입력은 보존되지만
  그 순간의 클릭과 이론상 겹칠 수 있음(실해 없음, 빈도 극히 낮음).
- **개발 중 코드 수정 시** 이미 실행 중인 생성 스레드는 구 코드로 완주한다.
- ~~검증 스크립트가 세션 스크래치패드(휘발 영역)에 있음~~ → **해결됨(§6)**:
  실제로 /tmp 정리로 테스트가 증발해 재작성해야 했고, 이를 계기로 당일
  `tests/` 승격을 완료했다.
- radio 외관(점 표시)이 세그먼트 버튼보다 덜 탭답다 — 기능은 동일.

## 5. 복원 포인트

- radio → segmented_control: `app.py` 내비게이션 블록 한 곳 교체로 복귀 가능
  (재클릭 해제 워트도 함께 돌아옴).
- 기능 전체 되돌리기: `--no-ff` 머지라 `git revert -m 1 87f9b58` 한 번이면 된다.
  증분 저장(#3)과 조합 회피(#9)만은 어떤 경우에도 유지 권장.
- 브랜치는 삭제됐지만 커밋은 main 이력에 남아 있다 — 포인터가 필요하면
  `git branch feat/background-generation 8ac1d52`로 재생성.

## 6. 당일 마무리 후속 (머지·테스트 승격·정리)

- **main 머지 (`87f9b58`, --no-ff)** — 머지 전 점검: 원격/로컬 정합(끼어든 커밋
  없음), 전 기능 테스트 통과, DB 스키마 변경 없음(읽기 쿼리만 추가), 신규 API는
  전부 기본값 있는 선택 인자, 윈도우 배포 파일 미변경. 머지 커밋 하나로 기능
  전체 revert가 가능하도록 --no-ff 선택.
- **`tests/` 승격 (`760d74f`)** — 세 세션에 걸친 휘발성 검증 스크립트를 pytest
  스위트 3개(test_db / test_generate / test_app_flows)로 재편. conftest의
  autouse 임시 DB 격리로 실사용 `data/`를 절대 건드리지 않음. 경로는 저장소
  상대 경로. Ollama 필요 테스트는 미연결 시 자동 스킵. `.gitignore`의 `*.txt`
  규칙이 `requirements-dev.txt`를 막고 있어 예외 추가.
- **이관 완결성 감사 → 갭 2건 발견·보완 (`33c16db`)** — "완벽하게 옮겼다"고
  답하기 전 대조 감사에서 동시성 테스트(생성 스레드 + 메인 검수 병행)와
  제출양식 컬럼 편집 테스트가 누락된 것을 확인하고 추가. 최종 29개 통과.
- **브랜치 삭제** — `merge-base --is-ancestor`로 전 커밋의 main 포함을 확인한 뒤
  로컬·원격 모두 정리. 저장소는 main 단일 브랜치로 마무리.
- 교훈: "다 옮겼다"는 기억이 아니라 **원본 목록 대조**로 답할 것 — 감사 없이
  답했다면 동시성 커버리지가 조용히 사라질 뻔했다.

## 7. 후속 사고: ① 생성 + ④ 추출 동시 실행 프리즈 (당일 저녁)

- **증상**: 생성을 걸어두고 추출을 동시에 실행 → 생성이 수 배 느려지고, 추출은
  버려진 듯 보이고, 모든 버튼이 먹통 → Ctrl+C 반복 → `Event loop is closed`
  트레이스 (최신 main, SANDBOX 클론에서 확인 — git 상태는 사용자 허락 후 열람).
- **원인 두 겹**: ① 로컬 Ollama는 요청을 순차 처리하므로 생성·추출이 서로의
  배치 뒤에 줄을 서며 둘 다 급감속. ② 추출이 화면(스크립트) 스레드에서
  timeout=600초 동기 HTTP 대기 → 소켓 대기 중에는 Streamlit이 실행을 중단할
  지점이 없어 세션 전체가 볼모(모든 클릭 무시). Ctrl+C 트레이스는 그 갇힌
  스레드들이 강제 종료된 이벤트 루프에 뒤늦게 보고하려다 난 **무해한 사후
  소음**이며, 증분 저장 덕에 데이터 유실은 없음.
- **판단 수정**: 추출 백그라운드화(C)를 처음엔 "비권장"했으나, 사용자 관찰
  ("추출이 꽤 오래 걸린다")로 전제가 틀렸음을 확인 — CPU에서 기사 추출은
  1~3분이 정상 범위라 동기 설계 자체가 UX 결함이었다.
- **조치**: 생성 잠금을 **LLM 공용 잠금**으로 승격(생성·추출 상호 배제, 버튼
  상호 잠금 + 사유 표시) / **추출 백그라운드화**(생성과 동일한 스레드+사이드바
  상태 패턴, 완료 시 ④에 후보 인계, 스레드 비정상 종료 가드) / 추출 타임아웃
  600→300초(잠금 점유 상한). 테스트 31개 통과(추출 E2E 포함).
- 교훈: **동기 네트워크 호출을 화면 스레드에 두지 말 것** — Streamlit은 소켓
  대기를 중단시킬 수 없다. 그리고 공유 자원(Ollama)이 있으면 동시성 설계는
  "빠른 쪽 하나"가 아니라 자원 단위로 직렬화할 것.
